DIAGNOSTIC FERMÉ — L'AGRÉGAT VERS TRANCHE REMPLIT AUX BORNES DU TYPE

Le poison 0x0101010101010101, c'est HUIT TRUE : la photo du watchpoint
(ancienne valeur 0x0001010101010101 = sept octets sur huit) montre la
cellule LINK remplie OCTET PAR OCTET par la boucle SIb de :
    DONT_MOVE( HIGH_BLOCK + 1 .. MAX_VPG ) := (others=>TRUE);

Le FINC contient le bug en toutes lettres, en deux temps :
1. CODE_ASSIGN (cible DN_SLICE) fait CODE_SLICE -> pile = @dst, len_dst
   ... puis DROP : la longueur de la tranche, correctement calculée
   (on la voit : ULw HIGH_BLOCK / SUB / INC / CLAMP0 / MUL), est JETÉE.
2. CODE_ARRAY_AGGREGATE recalcule son étendue depuis les bornes DU TYPE
   (COLLECT_DIMENSIONS -> _FST_1 := 0 [littéral], _LST_1 := MAX_VPG,
   _LEN_1 := MAX_VPG+1) et le CHOICE_OTHERS remplit _LEN_1 - _EMIS
   composants À PARTIR DU DÉBUT DE LA TRANCHE.

Conséquence arithmétique : chaque affectation d'agrégat à une tranche
écrit LEN(type) composants depuis le début de tranche — débordement de
(borne_basse_tranche - FST_type) octets AU-DELÀ du tableau, et
écrasement de la queue du tableau À L'INTÉRIEUR. Pour la deuxième
affectation : HIGH_BLOCK+1 octets de 0x01 après DONT_MOVE — droit dans
la cellule LINK. La première déborde aussi (1 octet de 0x00, silencieux).

Tout s'explique : _standrd.adb passe (aucun with -> HIGH_BLOCK petit ->
le débordement court meurt dans le padding), calendar/direct_io/
sequential_io crashent identiquement (fermetures transitives -> 
HIGH_BLOCK grand -> la cellule LINK est atteinte), le crash est
indépendant du contenu (toujours le même UNLINK), et le find pile
négatif du premier dossier (les frames vivent dans la zone statique
VAR, pas sur la pile C — r13 = 0x18e4a60).

RM83 4.3.2 : la contrainte d'index applicable d'un agrégat affecté à
une tranche est CELLE DE LA TRANCHE. Le correctif fait exactement cela :
la range de la tranche (AS_DISCRETE_RANGE, déjà sous la main — 
CODE_SLICE la lit) est passée à CODE_AGGREGATE, qui en surcharge la
dimension 1 (les tranches n'existent qu'en dimension 1, RM83 4.1.2 ;
les dimensions aplaties suivantes — composants tableaux — restent aux
bornes du type composant, correct). TOUTE la machinerie aval (LEN,
STR, comptage others, choix nommés) devient juste sans autre retouche.
Le DROP reste : @dst est déjà le départ de tranche, la longueur relue
devient cohérente. Nota : les bornes de tranche sont ré-évaluées (une
fois par CODE_SLICE, une fois par l'agrégat) — pures dans tout le
corpus ; consigné en commentaire.

CARNET (proposition n°146) : agrégat affecté à une TRANCHE — CODE_ASSIGN
jetait (DROP) la longueur de tranche et CODE_ARRAY_AGGREGATE remplissait
aux bornes du TYPE depuis le début de tranche : queue de tableau écrasée
+ (bas_tranche − FST) octets au-delà. Symptôme : segfault UNLINK de
WRITE_LIB (cellule LINK = 8×TRUE = 0x0101...), dépendant de HIGH_BLOCK
(_standrd immune, fermetures transitives touchées). Diagnostic : hardware
watchpoint sur la cellule LINK -> écriture prise sur le fait dans
MARK_DONT_MOVE_PAGES ; FINC : DROP de len_dst + _FST_1/_LST_1 littéraux
du type. Correctif : contrainte applicable = celle de la tranche (RM83
4.3.2), range de tranche passée à l'agrégat, dimension 1 surchargée.
Gardien : SLAGG_TEST (rouge 5 OK/3 ECHECS capturé). À recenser : autres
consommateurs d'agrégats qui jettent une longueur déjà calculée
(grep DROP au voisinage de CODE_AGGREGATE).
