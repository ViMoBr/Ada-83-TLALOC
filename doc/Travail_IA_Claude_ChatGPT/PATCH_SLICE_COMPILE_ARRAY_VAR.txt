RAPPEL DU DIAGNOSTIC
--------------------
Le FINC de LEX_IMAGE montre DEUX fois :

	; COMPILE_ARRAY_VAR ASSOC.TY non gere DN_SLICE

(TEMP_STRING dans BLOCK__5, TRONQ dans BLOCK__6).  Comme pour le patch
n 2 : ni COVAR_ALLOCATE, ni copie -- TEMP_STRING_disp et TRONQ_disp
restent des qwords non initialises, et la defaillance est DIFFEREE au
premier usage des donnees (ici : chez l'APPELANT, HASH_POS, qui recoit
par RETURN un data_ptr poubelle).  Troisieme membre de la famille
"operande sans doublet propre" : comparaison (n 1), initialiseur
composant (n 2), initialiseur tranche (n 3).

L'outil de copie existe deja : CODE_SLICE en mode SOURCE
(IS_DESTINATION => FALSE, ATTENTION le defaut de la signature est TRUE)
fabrique le doublet anonyme de la tranche -- data_ptr decale + info aux
bornes de la slice -- et laisse son @doublet en pile ; c'est exactement
le contrat du repli defensif DN_QUALIFIED (La ,0 puis BLKMOV).

NOTES DE LECTURE
------------------------------------------------------------------------
1. IS_DESTINATION => FALSE est OBLIGATOIRE : le defaut de la signature
   (expander.adb ligne 151) est TRUE, qui laisse @data + taille et non
   un @doublet -- l'ordre de pile serait faux pour BLKMOV.

2. En mode source, CODE_SLICE emet lui-meme les VAR/namespace du doublet
   anonyme et calcule data_ptr = @prefixe + (FST_slice - FST_prefixe) *
   COMP ; les bornes de l'info sont celles de la TRANCHE.  On n'extrait
   ici que le data_ptr ("La ,0") : la LONGUEUR de copie est prise cote
   DESTINATION (SIZ du type de la variable), comme dans le repli
   DN_QUALIFIED et le patch n 2.  Pour TEMP_STRING : 2 octets ; pour
   TRONQ : IMAGE'LENGTH-3 octets (SIZ dynamique de _TRONQ__type).
   Meme niveau de rigueur que l'existant : pas de check 5.2.1
   d'egalite des longueurs.

3. Le FINC attendu a la place de chaque commentaire "non gere
   DN_SLICE" : CO_VAR + Sa <VC>_disp (COVAR_ALLOCATE), La <VC>_disp,
   Ld <type>.SIZ / LI 8 / DIV, puis le namespace ANON_* du doublet de
   tranche fabrique par CODE_SLICE (motif identique aux ANON_664_45 /
   ANON_665_19 deja visibles dans les RETURN de BLOCK__5), La ,0,
   BLKMOV.

4. ATTENTION -- ce patch NE SUFFIT PAS a faire passer LEX : il repare
   le flux de donnees (TRONQ recevra une vraie copie), mais la CAUSE
   PREMIERE du CONSTRAINT_ERROR observe est en AMONT : LEX_TYPE'IMAGE
   est compile en CALL STANDARD.INTEGER_IMAGE_L11 (CODE_IMAGE,
   expander-expressions.adb ~2185) -- l'image POSITION (" 12") au lieu
   du litteral ("LT_ABORT").  D'ou IMAGE'LENGTH-3 <= 0, TRONQ nul,
   et TXT(TXT'LAST) dans HASH_POS qui leve le check bas (index -1 ou 0
   contre FST_1 = 1).  Voir la discussion : l''IMAGE des enumeres est
   un chantier a part (tables de litteraux par type).
